# 吸收第三方 Lean 形式化:完整框架与决策分析

> 分析对象:`a9lim/blam`(Lean 部分 3232 行,AGPL-3.0)与
> `nisizaki/frenv-lean4`(526 行,无许可证)。
> 分析日期:2026-08,基于两个仓库当时 HEAD 的实际内容。

---

## 1. 概念澄清:"吸收"在定理证明项目里意味着什么

在普通软件工程里,"吸收一个库"≈ 拷贝代码、统一命名、纳入构建。
**在定理证明项目里,这个直觉是错的**,原因是形式化成果有一个根本特性:

> **定理绑定于它的表示(representation)与依赖(dependency)。**
> 一个定理的陈述引用具体的类型(`Lambda`、`Term`、`Trm V C`)、
> 具体的编码(`encode : Lambda → ℕ`、BLC 位串)、具体的归约关系。
> 换一个表示,定理就不是同一个定理了。

因此形式化成果可以按**可迁移性**分层:

| 层 | 内容 | 可迁移性 |
|---|---|---|
| 1. 定理本身 | `confluence_theorem`、`¬ HasNormalForm t` | **不可迁移** — 绑定于具体类型与编码 |
| 2. 证明方法 | 并行归约证合流、ratchet 递推 | 可借鉴,需重写 |
| 3. 定义与 API 设计 | `RatchetCert` 证书格式、`ParStep` 索引化 | 可借鉴,需重写 |
| 4. 证书/工具格式 | "义务可判定化"的证书形态 | 可移植 |
| 5. 基础设施代码 | 替换引理、通用合流设施 | 仅当表示与依赖一致时可复用 |

所以"吸收"的正确形态**几乎从不是拷贝文件**,而是在这条光谱上选一个
合适的档位(见 §3)。

## 2. 吸收决策的六个维度

对任何候选仓库,先按这六个维度打分,再谈要不要吸收:

1. **表示兼容性**(Representation alignment)
   项类型是否同构?归约关系是否同一定义?编码是否一致?
   如果不同:把定理从 A 表示"传输"到 B 表示需要多少新工作?
   —— 传输代价 = 吸收的真实成本上限。

2. **完成度**(Completeness)
   是已证定理,还是陈述的义务(Prop 定义/axiom/sorry)?
   **吸收未完成品 = 继承对方的债务。**

3. **许可证**(License)
   目标出口决定许可证红线:若最终要进 mathlib(Apache-2.0),
   **任何 AGPL/GPL 代码都不可吸收**(污染且不可逆)。

4. **依赖画像**(Dependency profile)
   对方依赖 mathlib 吗?哪个版本?只依赖 `Init`(核心 Lean)吗?
   版本漂移意味着吸收后要维护对方 API 的兼容。

5. **目标对齐**(Goal alignment)
   对方做的是**理论定理**还是**数值测量/证书**?
   与我们的目标(λ ⟺ Partrec ⟺ TM2、Kolmogorov 复杂度理论)是否同一性质?
   —— 具体数值结果(如"第 35 位的 busy-beaver 记录")几乎从不属于理论库。

6. **维护成本**(Maintenance)
   review、命名改造、风格统一、上游漂移跟踪、测试。
   定理库的维护成本是**永久**的,不是一次性。

## 3. 吸收光谱:七档模式(从强到弱)

| 档 | 模式 | 定义 | 代价 | 收益 | 适用条件 |
|---|---|---|---|---|---|
| 0 | **完全吸收** | 文件并入本库,统一命名/风格/依赖 | 极高 | 完整成果 | 表示一致 + 许可证兼容 + 已完成 + 目标一致 |
| 1 | **重写吸收** | 同一组定理,在我们的表示上重述 | 高 | 成果等价 | 定理值得,表示不同 |
| 2 | **模块抽取** | 只取其中某文件/某组引理 | 中 | 局部成果 | 该模块自包含且与表示解耦 |
| 3 | **依赖引用** | `lake require` 保持独立仓库 | 低 | 不重复造轮子 | 对方活跃维护、API 稳定 |
| 4 | **想法借鉴** | 吸收"形式/设计",重写为我们的风格 | 低 | 方法论 | 如证书格式、证明骨架 |
| 5 | **互操作** | 数值对拍、测试 oracle | 很低 | 验证正确性 | 对方有可执行实现 |
| 6 | **交叉引用** | README/docs 互链 | 零 | 生态可见性 | 任何情况 |
| 7 | **论文引用** | 引用背后的论文/思想 | 零 | 学术正当性 | 思想来源 |

> 关键原则:**先定档,再动手**。默认档位是 6–7(交叉引用/论文),
> 只有六维度全部通过才升级到 0–1。

## 4. blam(3232 行 Lean)逐文件可吸收性分析

结构:核心 BLC 语义层 + 证书层 + qBLC 自解释。**不依赖 mathlib**(纯核心 Lean)。

### 4.1 核心语义层

| 文件(行数) | 内容 | 与我们的重叠 | 可吸收性 |
|---|---|---|---|
| `Term.lean`(132) | BLC 项,de Bruijn 索引 | 同为 de Bruijn,但编码是 BLC 位串 | 不吸收(表示不同) |
| `Step.lean`(159) | 头部归约可执行步进器 + 关系版 | 我们的 `Reduction.lean` 有归约关系;可执行步进器我们没有(用 `#eval` 可补) | 不吸收 |
| `Subst.lean`(136) | 5–6 条 shift/subst 方程(Nipkow–Berghofer de Bruijn 引理集) | **同一组引理**;我们的 `Syntax.lean` 有 10+ 条(lift/lift_subst/subst_subst…),是它的超集 | **零增量**,不吸收 |
| `Beta.lean`(138) | 全 β 归约、正规形、spine 纪律 | 我们的归约理论更完整(含并行归约、合流) | 不吸收 |
| `Par.lean`(206) | **索引化**并行归约(Accattoli–Faggian–Guerrieri 风格,按复制加权计数) | 方向不同:他们为证书服务,我们为合流服务 | 想法可借鉴(若做复杂度) |
| `Factor.lean`(260) | 头因子分解桥:`HeadDiverges → ¬ HasNormalForm` | 我们没有这个桥 | 形式可借鉴(§4.2) |
| `NoNf.lean`(123) | 旗舰定理:loop32 无正规形 | 我们证的是"发散不可判定"(元定理);他们是"这一项发散"(具体) | **不可移植**(对象是 BLC 位串) |
| `Wire.lean`(31) | BLC 线编码(kernel-computable) | 我们的 `Encoding.lean` 是 `encode : Lambda → ℕ` | 不吸收 |

### 4.2 证书层

| 文件(行数) | 内容 | 可吸收性 |
|---|---|---|
| `Sym.lean`(333) | 符号检查器(STerm 元变量,Rust `PTerm` 的 Lean 镜像) | 不吸收(绑定 Rust 工具链) |
| `Ratchet.lean`(259) | 通用 ratchet 证书 v1.2:义务是**可判定事实** | **形式值得借鉴**(§4.3) |
| `HeadTower.lean`(344) | v2 证书 | 同上 |
| `Selector.lean`(226) | v3 证书 | 同上 |
| `Passenger.lean`(233) | v4 证书 | 同上 |
| `Rigid.lean`(217) | rigid-head 论证 | 同上 |
| `Loop32.lean`(184) | 32 位记录持有者的证书 | 不可移植(具体位串) |
| `Certs.lean` + `Certs/Size32–41.lean` | 生成的证书(每个 ~10 行,import 全套证书机制) | 不可移植;且"生成代码"与我们的手工库风格相悖 |

### 4.3 值得吸收的"形式":RatchetCert

`RatchetCert` 的设计思想:**把"发散证明"打包成一个记录,其义务全部是
可判定的符号轨迹事实,从而可以被机器快速验证**。这对 busy-beaver 风格
的实证工作(枚举候选、逐个证伪)是正确架构。

- **吸收方式**:想法借鉴(档 4),不是代码搬运(档 0)。
  若未来做我们编码下的 BBλ 前沿,用我们的 `Lambda` 重写这个形式:
  ```lean
  structure RatchetCert where
    T : Lambda          -- 候选项
    obligations : ...   -- 可判定的发散义务(用 decide/native_decide 验证)
  theorem cert_forces_divergence (c : RatchetCert) : ¬ HasNormalForm c.T
  ```
- **代价**:为一个"将来可能做"的实证功能引入 2000+ 行证书机制,不划算。
  **结论:记为想法,不实现。**

### 4.4 硬约束:许可证

`blam` 是 **AGPL-3.0**。本项目目标出口之一是 mathlib(Apache-2.0)。
**AGPL 代码进入本库 = 永久污染**。仅此一条就否决档 0–2。
(即使不考虑 mathlib,AGPL 也要求整个衍生作品 AGPL,与本项目无 LICENSE
的现状冲突。)

### 4.5 可行的互操作(档 5):测试 oracle

blam 的 Rust 引擎可以**穷举小项的 K 值/发散性**,我们可以在 `#eval` /
`native_decide` 层面对拍我们的 `Lambda` 定义:
- 用 blam 的 BLC→de Bruijn 位串结果,与我们的 `Lambda.encode` + 求值器对拍;
- 验证我们 K 定义在小规模上的数值正确性。
**这不是吸收,是互操作**——零代码进入,双方各自独立演进。

## 5. frenv-lean4(526 行,2 文件)逐文件分析

| 文件(行数) | 内容 | 完成度 | 可吸收性 |
|---|---|---|---|
| `Basic.lean`(167) | `Trm V C`(命名变量 + 常量)、`BetaSigmaStep`、通用合流设施 | 完成 | 通用设施我们已有且更全;`Trm V C` 表示与我们的 de Bruijn 冲突 |
| `Par.lean`(357) | 并行归约、`sim`/`embed`(已证)、强合流**义务**(`overlap*`,10 条 Prop) | **主定理未证** — `ParStronglyConfluent` 只是 def | **吸收 = 继承未完成义务** |

要点:
- **同一个经典定理(λ 演算合流),但对象不同**:β+σ 环境演算 vs 我们的纯 β。
  定理级不冲突,mathlib 的 `Relation.Confluent` 是通用设施,两个具体实例
  可共存。
- **单 commit、无 LICENSE、2026-08-10 创建**:无许可证 = 无法合法吸收
  (连档 3 依赖引用都需谨慎)。
- **唯一价值是论文思想**:"lambda calculus with functionally referable
  environments"——若未来做**环境机器/显式替换求值器**(O(1) 替换),那是
  新工作,引用论文(档 7),不移植代码。

## 6. 什么时候吸收是对的(正例条件)

**完全吸收(档 0)需要五个条件同时成立:**

1. 表示一致(项类型同构,或传输代价趋近于零);
2. 许可证兼容(与目标出口一致);
3. 已完成(无 sorry/义务/axiom);
4. 目标一致(对方做的正是本库要的理论,而非测量/工具);
5. 维护成本可承受(review、命名、风格、漂移)。

**两个候选各缺哪几条:**

| 条件 | blam | frenv-lean4 |
|---|---|---|
| 表示一致 | ❌ BLC 位串编码 | ❌ 命名变量 + 常量 |
| 许可证兼容 | ❌ AGPL-3.0 | ❌ 无许可证 |
| 已完成 | ⚠️ 证书层完成,但绑定具体位串 | ❌ 主定理未证 |
| 目标一致 | ❌ 数值测量/证书 | ⚠️ 理论,但不同演算 |
| 维护成本 | ❌ 生成代码 + 2000 行证书机制 | ⚠️ 526 行小,但继承义务 |

→ 两边都不满足"完全吸收"的任何一条充分条件。**结论:不吸收。**

> 对照:mathlib 的 PR 机制本身就是"吸收"的正规通道 —— bors 合入 +
> 维护者 review + 全库 CI,是质量闸门。如果我们想把自研成果送进 mathlib,
> 走的正是这条路,而不是"把别人的代码搬进自己库"。

## 7. 对 M5(Kolmogorov 复杂度)的具体含义

**M5 的需求清单**(全部可在项目内部闭环满足):

| M5 需要 | 项目现状 |
|---|---|
| 项编码 | ✅ `Encoding.lean`(`encode`/`decode`) |
| 通用机(自解释器) | ✅ `SelfInterpreter.lean`(`E ⌜M⌝ ↠ M`) |
| 停机不可判定 | ✅ `Undecidable.lean`(`not_computablePred_codeConverges`) |
| s-m-n | ✅ `SMN.lean` |
| 不动点/第二递归 | ✅ `FixedPoint.lean`、`SecondRecursion.lean` |
| 不可压缩串(计数) | ➕ 新证(简单) |
| K 不可计算(Berry) | ➕ 新证(用第二递归定理) |
| 不变性定理 | ➕ 新证(用 `lambdaComputable_iff_tm2Computable`) |
| 前缀自由编码(若做 Ω) | ➕ 新造(机械) |

**两个仓库对 M5 的实际贡献:0 行代码。**

- blam:1 个想法(RatchetCert 形式,若日后做 BBλ)+ 1 个 oracle(数值对拍);
- frenv-lean4:1 篇论文引用(若日后做环境机器)。

## 8. 决策矩阵汇总

| 对象 | 建议模式 | 档位 | 具体动作 |
|---|---|---|---|
| blam 语义层(Subst/Par/Factor) | 不吸收 | — | 交叉引用;`Subst.lean` 与我们的 `Syntax.lean` 是同一组引理,零增量 |
| blam 证书层(Ratchet 等) | 想法借鉴 | 4 | 记入文档:若做 BBλ 前沿,用我们的 `Lambda` 重写 RatchetCert 形式 |
| blam 数值引擎 | 互操作 | 5 | M5 的 K 定义与 Rust 引擎小规模对拍(`#eval`) |
| blam 许可证 | — | — | AGPL 红线,永不进入本库 |
| frenv-lean4 全部 | 论文引用 | 7 | 若做显式替换求值器,引用 FREnv 论文,不移植代码 |

**最终建议**:吸收的本能冲动在定理证明项目里通常有害 —— 表示不兼容、
许可证污染、未完成债务,换来的收益几乎为零。正确姿势是把"吸收"降级为
**借鉴(想法)+ 互操作(验证)+ 引用(文档)**,把代码吸收留给 mathlib
的 PR 通道,把精力放在 M5 的自研定理上。
